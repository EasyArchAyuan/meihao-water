## 🔴 git 事故与恢复（重要）
- 现象：`git commit`+`push` 时 `rebase --autostash` 报 `f5f3b63f is not a valid object`、`Cannot autostash`，push 被拒；随后 `git log` 的 HEAD 竟回退到旧 `880ed78 (chore(release): 1.6.1)`，`git fsck` 报大量 `invalid reflog entry`（`31d6b99`/`39f2855`/`ec471aa` 等），`git reset --mixed` 报 `unable to read ec98e60…`。
- 根因：**本地 `.git` 的对象丢失**（只剩 1 个旧 pack，reflog/index 引用了不存在的对象）；**远端完好**（GitHub API 确认 `main = 39f2855`）。
- 恢复（依 `git-repo-recovery` 技能，流程 A）：① 备份 `.git`+关键工作区文件到项目外；② `git fetch origin main` 把缺失对象拉回（`39f2855` 变有效、`origin/main` 重建）；③ 损坏的 `.git/index` 用 **`mv`（非 `rm`）** 移出后 `git reset --mixed FETCH_HEAD` 重建 index（**保留工作区**，本轮 Caddyfile 修复未丢）。
- 备份目录：`C:/Users/shang/WorkBuddy/_mhsy-git-backup-1790063306`（含 `dotgit/`、`index.broken.bak`、worktree 关键文件）。
- 遗留：`.git/logs` 仍有几条指向已丢失对象的 reflog 行（`5c4fd1c`/`ed35708`/`ec471aa`），`fsck` 报 noise 但**不影响功能**；如需彻底干净可 expire 这些 reflog 行。
- 教训：**本机 `--autostash` 不可靠**。本项目后续提交：优先 `fetch` → `git merge --ff-only`；若需 rebase，先手动把无关未提交文件处理干净，不要依赖 autostash。

### 根因定位（第二次中断后查明）
- 第二次提交时 `rebase` 又被 SIGTERM 打断，之后 `git` 直接报 `not a git repository` —— 因为 **`.git/refs` 目录整个不见了**（git 判定仓库有效需 `refs`/`objects`/`HEAD` 齐备）。`mkdir -p .git/refs/{heads,tags,remotes/origin} .git/logs/refs/heads` 后即恢复识别（对象/`packed-refs` 都在）。
- 进一步探测：在 `.git/refs/remotes/origin/` 写探针文件 → **3 秒内可见、稍后自行消失**；`git update-ref refs/remotes/origin/main <sha>` 也**建不住**。→ **本机环境会在后台延迟清除 `.git/refs/` 下的松引用文件**（与本仓库中文路径 + safe-delete 已知问题同源）。
- 这解释了最初事故：松引用被清 + 对象被 prune → HEAD 回退到 `packed-refs` 旧值（`880ed78`），reflog 指向的对象全失效。
- **缓解（已实施）**：`git pack-refs --all` 把 `refs/heads/main` 打包进 `packed-refs`（现为 `a09efed`），松引用即使被清也能解析到正确 sha。后续每次提交推送后都补一次 `pack-refs`。`origin/main` 远程跟踪引用建不住 → 接受「`status -sb` 显示 gone」为已知现象（不影响 push）。
- 最终状态：`HEAD=a09efed`、`fsck` 干净、`git status` 干净、远端 `c31ac5d..a09efed` 已同步。
