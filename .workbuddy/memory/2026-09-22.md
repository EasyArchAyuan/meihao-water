### 根因定位（第二次中断后查明）
- 第二次提交时 `rebase` 又被 SIGTERM 打断，之后 `git` 直接报 `not a git repository` —— 因为 **`.git/refs` 目录整个不见了**（git 判定仓库有效需 `refs`/`objects`/`HEAD` 齐备）。`mkdir -p .git/refs/{heads,tags,remotes/origin} .git/logs/refs/heads` 后即恢复识别（对象/`packed-refs` 都在）。

## 🔴 站长平台「验证失败：302 网页存在跳转」→ 根因是 **304**（本轮真正解决）
- 报错文案换了（从「无法连接」→「302 网页存在跳转」），**这本身是进展**：说明百度已经能摸到服务器。
- **地面真相（全靠上一节装的访问日志）**：日志里百度蜘蛛对验证文件的请求是 `status:200 size:32` —— 服务端给的确实是 200。**两边都没说谎。**
- 用户在站长平台页面用开发者工具抓到决定性证据：该文件请求 **`状态代码: 304 Not Modified`**，响应头 `Etag: "dllus8f1fchsw"`、`Cache-Control: no-cache`。
- 🔑 **根因**：验证文件此前由 `file_server` 提供 → 带 `ETag`/`Last-Modified` → 检测端（浏览器发起）二次请求带 `If-None-Match`/`If-Modified-Since` → Caddy 命中后回 **304**。**304 属于 3xx 家族**，站长平台把 3xx 一律判为跳转 → 报「302 网页存在跳转」。**报错里的 302 是通用话术，不代表真返回 302。**
- ✅ **修法（已上线）**：验证文件**恒返回 200** —— 新增片段 `(verifyfile)`：`respond` + `Cache-Control: no-store` + 显式 `Content-Type`，**不用 file_server**（`respond` 不产生任何 validator）。主站块改互斥 `handle` 分组（`@baidu_verify` 在前、catch-all `handle { file_server }` 在后）；HTTP(80) 块同样切换，否则「绕开 TLS 的直出保险」会重新长出 304。
- 🐛 **坑：Caddy `import` 不支持前向引用** —— 片段 `(verifyfile)` 定义在使用点之后 → `caddy validate` 报 `File to import not found: verifyfile`。**片段必须定义在使用点之前。**（第 2 次 commit 才修好）
- ✅ 实测（改动后）：普通 GET 200 且 `ETag`/`Last-Modified` 均空、`Cache-Control: no-store`；带截图里那个 `If-None-Match` → **200**（关键）；带 `If-Modified-Since`（未来时间）→ 200；80 端口同一文件 200。回归：主站 6 个路径全 200、80 端口首页 301、旧域 3 个 301 一跳、图片防盗链 自有域 200 / 第三方 403、水邻居站 200。
- 服务器 `/etc/caddy/Caddyfile` sha256 `ac3d58af…` = 仓库 blob（逐字节一致），`caddy fmt` 零差异。
- 提交链：`088a869`(respond 恒 200) → `20e6075`(片段前移修 import 报错)。
- **通用判读经验（已写入技能）**：任何「平台说 3xx/跳转、我自测 200」的矛盾，**第一个怀疑对象是 304**。最快现场确认法：**清一次浏览器缓存后重测**（缓存一清条件请求就不带 validator）。延伸：一切「验证类接口」（各站长平台验证文件、支付回调校验文件、健康检查端点）都应**恒 200 + 禁缓存 + 无 validator**，不要交给静态文件服务托管。
